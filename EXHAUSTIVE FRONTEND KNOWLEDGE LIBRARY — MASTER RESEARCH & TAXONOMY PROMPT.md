# 4. IMPORTANT DISTINCTION

Do not confuse:

### A. Official technical concepts

with:

### B. Design patterns

with:

### C. Visual styles

with:

### D. Component variants

with:

### E. Marketing names

with:

### F. Library-specific terminology.

Keep them separately classified.

Example:

`button`

is different from:

`HTML <button> element`

which is different from:

`Primary Button`

which is different from:

`Glassmorphism Button`

which is different from:

`Material Design Button`

which is different from:

`Animated Button`.

Do not incorrectly treat all of them as the same technical concept.

# 50. DO NOT ARTIFICIALLY CREATE SUBTYPES

This is critical.

For example:

Do NOT create:

```text
Blue Button
Red Button
Green Button
Purple Button
```

as separate technical button types.

Those are merely color variations.

Instead classify:

```text
Button
→ Color
→ Theme
→ Variant
```

Likewise:

```text
Large Button
Small Button
Medium Button
```

should generally be treated as sizing variants, not separate button technologies.

Maintain semantic accuracy.

# 71. FINAL INSTRUCTION

Be aggressively exhaustive.

Do not stop at the commonly known frontend concepts.

Do not assume that a category is complete merely because it contains 50–100 entries.

For every category:

> **Research → Expand → Verify → Cross-check → Find omissions → Expand again → Verify again.**

But NEVER sacrifice factual accuracy for quantity.

The objective is not:

> “Create the biggest list.”

The objective is:

> **Create the most comprehensive, accurate, hierarchical, searchable, live-previewable frontend knowledge system that can realistically be built from verified information.**

If a concept cannot be verified confidently, mark it as uncertain rather than inventing information.

If two terms represent the same concept, preserve the aliases but maintain one canonical concept.

If a technology is obsolete, do not delete it; classify it correctly as legacy/deprecated/obsolete.

If a technology is experimental, label it accordingly.

If a concept is framework-specific, identify the framework.

If a visual style is merely a design pattern rather than a technical technology, classify it separately.

If a component has functional types, visual variants, states, properties, interactions and animations, model those relationships separately.

The final result should be suitable for powering a **large-scale interactive frontend encyclopedia and visual component playground**.
